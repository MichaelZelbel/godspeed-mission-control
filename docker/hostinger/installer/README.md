# Godspeed Mission Control prepared Hostinger installer

Live coordinator: https://godspeedmissioncontrol.com/godspeed-install, run by the website godspeedmissioncontrol.com since 15 October 2026 (its page is https://godspeedmissioncontrol.com/hostinger). The website copies its configuration from compose.mjs here, so this folder still decides what a buyer's server is given. The Node coordinator in this folder is the reference implementation: GitHub CI runs it, and it is what you deploy to run a coordinator of your own.

The public checkout file is `docker/hostinger/one-click.yaml`, generated by `node docker/hostinger/installer/public-compose.mjs`. The documented Hostinger button can name this public file at an immutable GitHub commit. It has no buyer credentials, private callback key, hostname field or setup field. Its two images stay pinned by digest. It detects the VPS hostname, creates a random private setup code once in its persistent volume, starts the existing complete application, and registers that server with the website over HTTPS. The private per-installation Compose URLs remain available for earlier installation links; they are not the public checkout file.

## Public-file ownership contract

The public file alone proves no buyer's identity. A public first visit or knowledge of a hostname never creates an owner account. The website must first verify a fresh Hostinger sign-in against the official VPS API and confirm that the signed-in person owns the selected VM, hostname and IP address. Only then may it obtain and disclose the application's private, single-use account-creation invitation.

The server posts `{hostname, setup}` to `https://godspeedmissioncontrol.com/godspeed-install/api/servers/register`, sending its 64-hex private code in the TLS request body only. The coordinator must verify that the hostname's DNS resolves to the request's trusted source IP. Resolver failures are retried, never accepted as proof. It returns 202 only after an encrypted, durable, 24-hour registration is stored. Repeating the same registration keeps the same secret and atomically renews its 24-hour expiry; a different code for an active registration returns 409. A mismatch returns 403; rate limits return 429; unavailable configuration or transient failures return 503.

The bootstrap waits for application health and checks the existing local `/api/auth/status` endpoint. Until an owner is configured, it renews its registration every 20 minutes after a durable receipt. Failures keep retrying with a pause growing from five seconds to five minutes, without a lifetime cutoff, so a delayed checkout or lost coordinator record does not require a manual server restart. Once the local app reports an existing owner, enrollment stops. No response body becomes a credential, no request follows a redirect and no setup code is logged. The bootstrap does not call the owner invitation endpoint itself.

The public manifest and generator received unit, Docker Compose parsing and shell syntax checks on 17 October 2026. That work did not execute the public installer or change a VPS. The new registration/OAuth endpoint and the paid provider handoff still need their own verification before an end-to-end success claim.

Hostinger describes the checkout handoff and referral parameter here: https://www.hostinger.com/support/deploy-on-hostinger-button/

The first paid checkout on 17 October 2026 exposed separate Hostinger handoff and URL-fetch failures and a conflict with its preinstalled Traefik. Manual recovery of that server was not proof of the automatic flow. The purchase-to-deployment handoff still needs a successful automatic retest; local runtime checks alone do not establish that it works.

The generated deployment now uses Hostinger's existing Traefik on ports 80 and 443 instead of binding those ports again. Traefik passes TLS for the VPS hostname to the project's internal Caddy container. Caddy detects the hostname, obtains and renews the certificate using TLS-ALPN-01, and proxies to Godspeed. The default Hostinger template uses HTTP-01 for its own certificates, so its TLS-ALPN traffic remains available for passthrough. No Docker socket, provider changes, extra hostname field or setup code is needed by the Godspeed project. This targets template 1210 as observed on 17 October 2026: host networking, Docker discovery and the `websecure` entrypoint. A differently configured Traefik is a different deployment target.

## Coordinator deployment

To run a coordinator of your own: copy this folder to /opt/godspeed-hostinger-installer and install godspeed-installer.service, with GODSPEED_INSTALL_ORIGIN set to your coordinator's public HTTPS address. Its GODSPEED_INSTALL_BIND must be the actual Docker host-gateway address (inspect Docker's bridge network). The former test machine used 10.0.0.1. The coordinator is not exposed publicly on that HTTP port; the generated Caddy configuration proxies /godspeed-install over HTTPS when deployed on the coordinator's own server. Other buyer servers use HTTPS directly and do not proxy the coordinator.

For a coordinator deliberately deploying to a bare Docker server without Hostinger's Traefik, set `GODSPEED_INSTALL_HTTPS_PROXY=standalone`. That explicit mode publishes Caddy on 80/443 as before. It is also retained as a separate generic-host test; it is not a substitute for the Hostinger-template test.

The generated configuration says nothing about Telegram. The buyer connects a bot on their own server's web page after the account is made (../README.md, "Telegram, connected after the account"), so a bot's key never reaches this coordinator, the website or its logs.

DynamicUser and StateDirectory keep private jobs in /var/lib/godspeed-installer, retained through restarts. Browser, callback and Compose credentials are separate.

The generated Compose file carries no setup code (since 6 October 2026). On its first start the server makes its own, keeps it in its data volume, and sends it with the authenticated hostname callback; the first callback binds both the server address and that code, and the Compose link opens nothing after it. Hostinger fetches and keeps the Compose file, so a setup code written into it reached Hostinger and anyone who saw the link. The callback is accepted only from an address the claimed hostname actually resolves to (A/AAAA), so the callback secret alone, scraped from the Compose link in a browser's history, cannot bind the job to a stranger's server; a transient resolver failure is allowed because the real server keeps retrying, and GODSPEED_INSTALL_VERIFY_HOST=0 disables the check where a deployment's DNS makes it impractical.

Limits: an installation whose Compose file was never fetched expires after one hour, a deployed one after 24 hours. One client (the address Caddy names in X-Forwarded-For, and for IPv6 its whole /64, since a customer is handed a /64) holds at most five installations not yet bound by the authenticated hostname callback and starts at most twenty a day; overall at most thirty start per minute. Fetching your own Compose link no longer counts as "deployed" for that cap, so it cannot be used to escape it. Before, the Origin header was the only gate and one global cap of 100 jobs kept for a day let a script block real buyers. These per-address counters are persisted to the private volume (limits.json, keyed by a salted hash of the client group, never the address itself), so a restart no longer resets them. Never log generated configurations, ticket files, invitation links, authorization headers or job state. No customer AI traffic is routed through the coordinator.

The coordinator reads a claimed server's callback reply with a hard few-KB cap: a flooded reply (64 MB under the service's MemoryMax=96M) used to crash the Restart=on-failure service, and the persisted job made every restart crash again.

seed-vps-test.mjs is only an operator tool for the authorized test VPS; it generates and stores a synthetic private ticket and Compose configuration in /opt/godspeed-hostinger-test. It is not part of the customer flow.

## Verification

Run `node --test docker/hostinger/installer/test.mjs`. On a disposable Linux Docker host with ports 80/443 free, run `GODSPEED_TEST_DOCKER=1 node --test docker/hostinger/installer/test-traefik.mjs`. It starts the exact default Hostinger Traefik configuration with pinned test images, uses Pebble to actually validate a TLS-ALPN challenge through Traefik, then checks the callback, private owner creation, persistent session and application restart. It never bypasses ACME validation or contacts a public certificate authority. It removes only its temporary projects and volumes. The workflow_dispatch docker workflow option hostinger-automatic runs this plus the standalone Docker/browser path with the complete pinned application image. Docker config --variables --format json must return an empty object for the buyer's generated configuration.

Live test results: private owner invitation; account creation without setup code; 12-character progress; 30-day login; requested-page return; incorrect-password feedback; logout revokes server session; synthetic expiry shows the expiry message; sign-in again returns to the requested import page.
