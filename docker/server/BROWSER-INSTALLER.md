# Existing Hostinger VPS browser installer

`install-browser.sh` is the website's authenticated SSH entry point. The public
checkout file remains `docker/hostinger/one-click.yaml`; `install.sh` remains the
existing human one-line installer.

The website must verify fresh Hostinger OAuth ownership, VM hostname and IPv4,
then attach a new temporary SSH key to that exact VM. Download this wrapper from
an immutable commit, with `GODSPEED_RAW` set to that same raw GitHub commit root.
Run `bash install-browser.sh --detach` and supply one canonical JSON line on stdin:

```json
{"job":"64 lowercase hex characters","callback":"64 lowercase hex characters"}
```

These are a job identifier and a fresh completion bearer, generated by the
website. They are never shell arguments. Launch returns only
`{"ok":true,"state":"started"}` or a fixed error JSON. Revoke that exact temporary
key with Hostinger's per-VM SSH-key API after launch, including failure paths.
Do not log or persist its private key for later SSH polling. The wrapper does not
edit `authorized_keys` or use an account-wide key-delete shortcut.

The detached supervisor runs for at most 28 minutes plus its short forced-exit
grace and 55-second completion delivery window. It posts over IPv4 HTTPS to the
fixed origin `https://godspeedmissioncontrol.com` at
`/godspeed-install/api/hostinger/complete/<job>`, with `Authorization: Bearer
<callback>`. Curl reads the bearer and result from root-only files, follows no
redirects, and accepts HTTP 200, 202 or 204 as acknowledgement. Metadata, callback
configuration and result files are erased after acknowledgement or delivery
expiry. The website must expire jobs without a valid callback after 30 minutes.
Completion is best effort if the VM is powered off or cannot reach the website.

The final private result is exactly one object:

```json
{"ok":true,"state":"installed","hostname":"srv123.hstgr.cloud","mode":"traefik","url":"https://srv123.hstgr.cloud/setup#invite=<64 lowercase hex>"}
```

`state` is `installed` or `existing`, `mode` is `traefik` or `standalone`, and the
same-server URL ends in `/setup#invite=<64 lowercase hex>` or `/login`. Failure is
`{"ok":false,"error":"fixed_error_code"}`. The callback receiver must enforce the
job bearer, expected VM IPv4, exact hostname and exact URL grammar before saving
or returning a result to its authenticated browser. Never put a result in logs.

The wrapper reads `/etc/hostname`; no hostname or setup code is entered by the
person. Existing Godspeed containers return their account page without pulling,
updating or recreating them. An existing account returns `/login`. New installs
preflight CPU, disk, filesystem, ports, proxy routes and existing Godspeed Docker
resources. Unknown port owners or conflicting routes fail before package changes.
On plain Ubuntu/Debian it installs Docker with the existing apt-lock/retry helpers
and runs standalone Caddy. The known Hostinger host-network Traefik keeps ports
80/443 and routes TLS through to an unbound Caddy container. Other applications,
proxies, Docker resources and OS data are never stopped, pruned or reinstalled.

Application settings and data remain in `/opt/godspeed-mission-control-browser`
and the own Compose project's persistent volumes. Failure never deletes them.
A later explicit attempt preserves a detected existing app and refuses orphaned
resources rather than silently adopting or replacing data.

Source checks: `node --test docker/server/test-browser.mjs`. On Linux with Docker
Compose, set `GODSPEED_TEST_COMPOSE=1` to include Compose config parsing. These
checks mock package/Docker/SSH effects and never start application containers.
They do not establish a successful live Hostinger installation.
