# Candidate release contract

Channel: full-alpha. Record format: 1. Notebook runtime: Node 22.19.0, on Windows x64 and Linux. Every bundle records the exact kit commit, bootstrap commit where applicable, pinned runtime hashes, licenses and checksums. The reused notebook is AGPL-3.0-only; its complete corresponding source and original license are included. The surrounding kit and public add-ons retain their original licenses. No binary stable release is published by this branch.

VPS uses a distinct Compose project, candidate volumes and isolated ports. Its primary process is the shared notebook, with an optional supervised computer relay. Default access is localhost port 47832 and Caddy HTTPS port 48443 with a local CA. Access requires an opaque candidate token or a five minute, single-use login link. Sessions expire after eight hours and use HttpOnly, Secure, SameSite cookies. The bot is off until a separate candidate token and owner are supplied. No live VPS deployment is performed by this build.

Windows uses its own installer AppId, application directory, startup shortcut and state directory. Defaults are per-user, without administrator rights. The workspace is a separate empty Full Alpha folder. Setup verifies every packaged payload hash. The candidate owns a separate Hermes home and desktop data directory; another installed Hermes executable may be reused only with this isolated profile. Fresh machines provision the pinned Hermes source and native desktop with the vendored MIT installer. Initial provisioning needs internet access and can take several minutes. Managed Git is added only to the candidate process path.

Hermes opens in the workspace, reads its skills and connects to the local notebook MCP. VPS Hermes uses a scoped local key, held outside synced records. Optional computer connection has its own state and port; it stays off until explicitly configured and paired. Source for the public coach, journal, phone and video tools is included. Provider credentials and optional accounts are never inherited from the maintainer.

Candidate native assistant conversations and work metadata use the file-authority adapter, including SQLite sequence and schema preservation. Synced logical snapshots and their history are included in knowledge backups. The Windows provisioner uses checksum-verified uv 0.12.12 and the pinned source's frozen Python/voice lock and npm lock; failed locked installs stop rather than re-resolving dependencies. Its process search path is deduplicated and it never disables shared scheduled tasks or kills launchers by image name.

An upgrade stops only the matching candidate process, creates a checked knowledge/media backup and retains workspace, provider choices and ownership. Additive initialization never replaces user-edited starter files. Uninstall removes only candidate software and startup, preserving knowledge and state. Retain the prior installer/bundle for rollback; format 1 has no destructive migration. Device settings and credential-bearing backups need private storage and must never be uploaded as the knowledge repository.

Backups include records, history, conflicts, readable workspace documents, binaries and a SHA-256 manifest. Device configuration has a separate private backup section. Normal restore requires empty knowledge/media destinations and does not restore credentials. Explicit device restoration is opt-in, only to an unconfigured candidate; settings are never silently adopted on another device. Windows upgrade also retains its installation and isolated Hermes directories outside application files. VPS volume recovery can restore those directories separately.

The user-only boundary is trial installation and optionally provisioning a separate VPS/Telegram account, then testing copied data on the desktop and laptop. Production deployment, live migration, Menerio retirement and stable publication require a later explicit approval. A synthetic installation test cannot establish those live outcomes.
