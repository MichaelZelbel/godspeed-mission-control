# Candidate release contract

Channel: full-alpha. Record format: 1. Notebook runtime: Node 22.19.0, on Windows x64 and Linux. Every bundle records the exact kit commit, bootstrap commit where applicable, pinned runtime hashes, licenses and checksums. The reused notebook is AGPL-3.0-only; its complete corresponding source and original license are included. The surrounding kit and public add-ons retain their original licenses. No binary stable release is published by this branch.

Matching test interfaces use the already checked Windows frontend in the Linux build. Put its exact package manifest at `notebook/ui/godspeed-prebuilt-frontend.json` and its browser files in `notebook/ui/dist`, then build with `REVISION` equal to that manifest's exact source revision and `USE_VERIFIED_FRONTEND=1`. The build rejects another revision, changed or additional assets, unsafe paths and redirected files. Ordinary builds without that explicit option still compile the frontend from source. Platform builds alone do not prove identical browser files; compare the installed hashes before asserting that correspondence.

VPS uses a distinct Compose project, candidate volumes and isolated ports. Its primary process is the shared notebook, with an optional supervised computer relay. Default access is localhost port 47832 and Caddy HTTPS port 48443 with a local CA. Access requires an opaque candidate token or a five minute, single-use login link. Sessions expire after eight hours and use HttpOnly, Secure, SameSite cookies. The bot is off until a separate candidate token and owner are supplied. No live VPS deployment is performed by this build.

Windows uses its own installer AppId, application directory, startup shortcut and state directory. Defaults are per-user, without administrator rights. The workspace is a separate empty Full Alpha folder. Setup verifies every packaged payload hash. The candidate owns a separate Hermes home and desktop data directory; another installed Hermes executable may be reused only with this isolated profile. Fresh machines provision the pinned Hermes source and native desktop with the vendored MIT installer. Initial provisioning needs internet access and can take several minutes. Managed Git is added only to the candidate process path.

Hermes opens in the workspace, reads its skills and connects to the local notebook MCP. VPS Hermes uses a scoped local key, held outside synced records. Optional computer connection has its own state and port; it stays off until explicitly configured and paired. Source for the public coach, journal, phone and video tools is included. Provider credentials and optional accounts are never inherited from the maintainer.

Candidate native assistant conversations and work metadata use the file-authority adapter, including SQLite sequence and schema preservation. Synced logical snapshots and their history are included in knowledge backups. The Windows provisioner uses checksum-verified uv 0.12.12 and the pinned source's frozen Python/voice lock and npm lock; failed locked installs stop rather than re-resolving dependencies. Its process search path is deduplicated and it never disables shared scheduled tasks or kills launchers by image name.

An upgrade stops only the matching candidate process, creates a checked copy of what an update can change (every durable path but `work/` and the assistant's undo archive) and of the media, and retains workspace, provider choices and ownership. In a workspace that is the top of its own Git repository the copy holds only the files whose bytes are not those of the current commit, the names of deleted committed files, and a ref (`refs/godspeed/update-copies/<copy>`) that keeps that commit; elsewhere it copies those paths whole (`notebook/core/update-copy.mjs`, `godspeed.mjs backup FOLDER --before-update`; restore through `godspeed.mjs restore FOLDER [--repository PATH]`). Once the upgrade worked, the copy it made is kept and every older one is removed with its ref (`notebook/core/upgrade-copies.mjs`); a failed upgrade removes none. Additive initialization never replaces user-edited starter files. Uninstall removes only candidate software and startup, preserving knowledge and state. Retain the prior installer/bundle for rollback; format 1 has no destructive migration. Device settings and credential-bearing backups need private storage and must never be uploaded as the knowledge repository.

Backups include records, history, conflicts, readable workspace documents, binaries and a SHA-256 manifest. Device configuration has a separate private backup section. Normal restore requires empty knowledge/media destinations and does not restore credentials. Explicit device restoration is opt-in, only to an unconfigured candidate; settings are never silently adopted on another device. Windows upgrade also retains its installation and isolated Hermes directories outside application files. VPS volume recovery can restore those directories separately.

The user-only boundary is trial installation and optionally provisioning a separate VPS/Telegram account, then testing copied data on the desktop and laptop. Production deployment, live migration, Menerio retirement and stable publication require a later explicit approval. A synthetic installation test cannot establish those live outcomes.

## Before a release that touches the goal loop

A release that changes how a goal is researched, decided or carried out (`tools/goals.js`, `mc-research`, `check-research.js`, `mc-decide`, `check-moves.js`, `work.js`, `mc-work-run`, the `goal-research`, `next-action` or `work-item` recipe, or the routines a first goal starts) is published only when both of these passed for the kit commit it ships:

- [ ] The goal-day acceptance passed on the server for this kit commit, before publishing. On the server, as root, run the copy in the engine the server keeps current (engine main `f8ae70a` or later), detached so a dropped ssh cannot end it: `systemd-run --unit goal-day-acceptance --collect bash $ENGINE_CHECKOUT/scripts/acceptance/goal-day.sh --kit-ref <the full commit main becomes when published, e.g. the head of release/second-edition-publish> [--pin-kit-ref]`. It holds that commit inside a throwaway container (the commit must be on GitHub, on any branch), installs it with that commit's own install-godspeed.sh as the throwaway user `gstest` (the server's own notebook service is never touched), checks the commit actually installed, checks that the first goal started every routine the installed `notebook/core/starting-routines.mjs` names (seven on the beta of 18 October 2026), and runs a founding research night, a decision and the work step with the real Claude Code. The work step takes the first bet on the goal card whose work item the mission control does itself (OWNER godspeed) and, unless the decision run already did it, runs `mc-work-run` on it; the item must end `STATUS: verified` with a line `VERIFIED check passed (...)`, and a work run's `answer.txt` must hold its `RESULT:` line. It ends with `ACCEPTANCE PASSED (kit <commit>, ...)`. Founding research takes up to an hour, the decision up to fifty minutes and the work up to half an hour, so a run can take up to about two hours (`journalctl -u goal-day-acceptance -f`). Its log is `<private acceptance log> time>/run.log` on the server; its "kit commit under test" and "installed commit" lines must name the commit being released, and the release record names the log's path.
  - `--pin-kit-ref` runs the installer with its product and starter pins rewritten to the commit under test, as a release of that commit would pin them. It is needed for the head of a branch whose release commit does not exist yet: the beta branch's `install-godspeed.sh` still pins the product of the last release (`6996712`). A release commit already pins what it ships; test that one without the switch, so its installer runs exactly as published.
  - `--standin FILE` is a rehearsal: FILE plays Claude Code, no token is used, and the run ends `REHEARSAL PASSED` or `REHEARSAL FAILED`, never `ACCEPTANCE`. It proves the script's own steps on any computer with Docker, never the assistant, and is never evidence for a release.
- [ ] The clean-install test's `linux-fresh` job passed on this commit, with its stand-in assistant: the private clean-install test repository, test branch `release-<product short commit>` made from the branch `v2` (rebuild.sh in `docs/full-version/release-2026-10-09/` makes it; `v2` holds every version 2 check, step "A whole goal day on the first goal", `scripts/v2/goal-day-checks.sh`). When GitHub refuses that private repository's jobs, run the job in a throwaway container on the test server as its `local-linux/README.md` says.

Since `v2` 3fad06a the clean-install test's `linux-fresh` job also runs the work and the daily round with its stand-in: its goal-day step runs `mc-work-run` (the item ends with `VERIFIED check passed (`, and a step whose check fails stays attempted), `godspeed-daily-round-work.py` ("Done, as you allowed:") and `godspeed-daily-round-choose.py` ("Going out unless you say stop:" on a day with no morning brief), and checks every routine in the installed `STARTING_ROUTINES`. It runs locally with `bash local-linux/wsl-job.sh fresh --log-dir <folder>` from a test branch made by rebuild.sh; set `PREVIOUS_RELEASE` and `PREVIOUS_PRODUCT` in that branch's `release.env` by hand. It passed against `77e2303`. Both of those run a stand-in or Claude Code, not the reader's own model through Hermes. The whole loop with Hermes is `notebook/test/acceptance/goal-loop-wsl.sh`, from Git Bash on a Windows PC with WSL 2: `OPENROUTER_TESTS_API_KEY=... bash notebook/test/acceptance/goal-loop-wsl.sh --commit <the full commit, pushed> --model qwen/qwen3.7-flash`. It installs that commit in a fresh Ubuntu 24.04 distro with the commit's own installer, connects the AI through Settings > Your AI, names a fictional goal and its weekly number in the notebook, runs research, a decision and the work with Hermes (the first day dated eight days back), tells a reading through the notebook, settles, lets Hermes' own daily-round routine make the next decision, reads the Goals page back, and ends with `ACCEPTANCE PASSED`, `ACCEPTANCE FAILED: ...` or `ACCEPTANCE STOPPED: ...` (the key's credit fell under its floor). Since its research writes its records properly (18 October 2026), a run with that model can cost about $1.50; `--floor <dollars>` stops it before a step when the key's credit falls below that. A free model, `--model nvidia/nemotron-3-super-120b-a12b:free`, costs next to nothing, but OpenRouter gives an account 1,000 free-model requests a day and a run makes a few hundred, so use a key whose account no other job needs free models from that day. The harness gives the reader's git a copy of the product at the commit, so the commands on the PATH are that commit's own (kit-bootstrap would otherwise install them from the default branch), and checks that they are. Its logs and what they showed: `docs/full-version/evidence/goal-loop-2026-10-18/`.
