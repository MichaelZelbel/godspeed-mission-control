# File sync contract, format 1

The authoritative meeting point is an owner-selected private GitHub repository. Before enabling uploads, unauthenticated GitHub lookup must return 404 and authenticated Git transport must successfully read it. Public repositories and URLs containing credentials are refused. Git credentials remain with the device credential manager. A new empty remote is supported; a GitHub account or repository is never created by setup.

Records use stable UUIDs plus readable IDs with UUID suffixes. Imported IDs and slugs remain unchanged. A record's identity is the `id` and `uid` in its file, never the file's name: a page a person reads is named after its title and sits in its folder (`file-format.md`), so a title, name or folder edit renames or moves the file, and every reference, which is by UUID, stays valid. Explicit id renames retain the previous ID as an alias and atomically rewrite typed references, and keep the file. Removals are tombstones, which leave the readable folders for the system folder. A page deleted by hand (in Obsidian or any editor) in a knowledge repository of its own is kept as a tombstone on the next sync, so the removal reaches every machine and a reference to it stays valid; until 6 October 2026 it left as a plain removal that every other machine then refused for good. Bookkeeping that a machine prunes (old run receipts, `job_receipts`, and earlier versions of jobs, `record_history`; `deletableTypes` in `file-policy.mjs`) is the exception: its removal travels as a removal, without a tombstone and without review on the other machines. Event edits are appended corrections; prior events remain unchanged. Histories preserve source UUID and exact earlier snapshots.

The reconciler takes the same exclusive workspace lock as record edits, validates, commits only permitted durable text, fetches, merges in a separate disposable worktree, validates the complete result and publishes through the transaction journal, putting every record at the file the merge gave it so that every machine names it the same. A document that a program not taking the lock (an assistant writing its journal, an editor) wrote after the round committed it is not overwritten: it stays as it is, and the merged version is saved for review. A device set up on a plain folder that joins a repository which already has commits builds on that history: the notebook's same-named documents win over the device's starter copies, and records are merged by identity, so a note written before joining stays. Its commits carry the Godspeed Mission Control identity, so a machine without a Git identity of its own still commits. A Git lock file older than fifteen minutes while no Git runs on the machine is one a killed Git left behind and is removed; a younger one, or any while a Git runs, means Git is busy. It never force-pushes, rebases user work or puts Git conflict markers in notes. A network failure leaves the local files available and records pending status. Existing externally staged files outside permitted state stop uploads. File names are read from Git exactly (null-separated), since a title with an umlaut or an emoji is a file name.

Concurrent same-file edits save base, local, remote and remote commit in conflicts/. Both versions remain readable until the owner chooses one or supplies merged text. An explicit resolution is reused only against that recorded remote commit. A saved conflict about a record follows the record by its UUID, so it can still be resolved after the record's file was renamed. Broken references, invalid files and unproven remote deletion stop publication. A remote removal without a tombstone or proven rename is saved as a review item for that record (its version here, none from the other side): choosing the removal makes the record a tombstone here, choosing to keep it brings it back in the next merge. Choosing a version that is missing removes the file in any review: a record becomes a tombstone, any other file is deleted. Independent offline edits retain distinct identities and converge. Immutable history records have deterministic IDs to avoid false cross-device conflicts.

## Renames and moves

Git is never allowed to infer a rename from content: its merges here use strategies that detect none and its diffs run with `--no-renames`, so it sees a renamed page as one file deleted and another added. Before any file of a merge is called a conflict, the reconciler reads the records the two sides touched on the merge base and on both sides and merges by record, by the UUID in the frontmatter (`notebook/core/sync/identity.mjs`), in both modes below:

- A record changed on one side only arrives as that side has it, where that side put it: a rename syncs as a rename, and the old file goes on every machine.
- A record moved on either side (renamed, moved to another folder, trashed, removed) and changed on both is merged field by field, a text field line by line. A rename on one machine and an edit on another end as one record with both changes, in the renamed file. When both changed the same field differently (two different titles), this machine's version stays, once, and base, local and remote are saved in `conflicts/` as one review item; the other version never lands as a second file.
- Two records that want one file name (the same title created on two machines offline, or a rename into a name the other side used) both stay: the one this machine already had there keeps the name and the other gets ` 2`, ` 3`. Names are compared as a file system that ignores case does. A page that is not a record keeps its name over a record.
- A record moved without being changed (an item whose collection was renamed) stays where the moving side put it.
- A record changed on both sides at the same file is merged field by field too: every save rewrites its `modified:` line, so a line merge never took two edits of different fields. Only two different edits of one field go on to the line merge below, and so to review; a record must still read as one afterwards. A title changed only in letter case renames the file, also where the file system ignores case.
- A page in the notebook folder that is not a record syncs like any other document, never as a record.

A change that moves many records at once (renaming a folder, converting a workspace) is not a mass removal: the removal guards count only records whose UUID is gone from every path. A removal of more than 25 records of one type that are also more than a fifth of that type's live records, pages and the notebook's own records in `_system/` alike, is stopped before it leaves a machine and again when it arrives; the bookkeeping a machine prunes (run receipts, history snapshots) counts on neither side of that. One stopped on its way out says to restore the files or remove the records in the notebook. One stopped on arrival is saved as one review item for the whole removal: keeping the records brings them back on every machine in the next merge; accepting the removal lets it through.

A name Windows cannot hold (a colon, a question mark, `aux.md`; `windowsInvalid` in `file-policy.mjs`) never enters the repository: such a file stays on the machine that has it, one an older version committed is untracked there, and a commit from an older version that carries one is merged without it, so a Windows machine keeps syncing everything else. Through the mission control's own repository the notebook never commits one; one the owner's own Git committed is named in the sync status of a Windows machine, to be renamed where it was made. Records and readable workspace documents sync as files. SQLite, device configuration, credentials, media binaries, node_modules and secrets never enter the knowledge repository. Media uses authenticated HTTP, one-time pairing and persistent device keys. SHA-256 checks every transferred binary. A content-addressed byte file and mapping preserve the storage path. Same-path different bytes create a review item with both versions; keep-both gives the local version a unique retained path. Tombstones propagate only against the same content hash. Bytes are retained for recovery. Offline choice is all media or selected already downloaded paths; selected mode does not evict existing bytes automatically.

## Through the mission control's own repository

A mission control that is already its own private repository, cloned to its owner's machines, can carry the notebook in that same repository instead of a second one (`godspeed sync folder`, which writes `{"repository":"folder","paths":[...]}` to `.godspeed/sync-config.json`). Two carriers delivered every file twice: a file committed on one machine reached the next as an untracked copy through the notebook first, and that machine's own `git pull` then refused to overwrite it. Setup refuses unless the repository is private, on its branch, and already ignores `.godspeed/`, `conflicts/`, `FULL-ALPHA.md` and, unless it is carried, `assistant-state/`. It never edits the owner's ignore file, config or hooks, and sets an older `.godspeed/sync.git` aside without deleting it.

The installers join a computer to a mission control already on GitHub by cloning the address the reader gave and running `godspeed sync folder` with no paths (`joinRepository`). A repository that tracks anything outside the shared paths is an owner's own mission control repository, and joins in this mode with `notebook/` only, as envy and x30 do. A repository that tracks nothing else (`.gitignore` aside) is a copy a notebook made through Settings, and is connected the way Settings connects it (`{"enabled":true}`, the same full list, the policy's ignore file); every tracked file a clone wrote with CRLF where the copy holds LF is given back as committed, once, so a document changed on another machine is taken rather than kept for review.

In this mode the reconciler shares the repository with its owner's sessions and scheduled pulls, so it follows their rules rather than its own:

- It commits only its own paths: `notebook/` by default, or every shared path (`"*"`) on a machine where nothing else commits, such as a server. It commits exactly those files, as a commit built in an index of its own, so whatever the owner has staged stays staged and out of it; notebook pages go in byte for byte. A page that one of the owner's ignore rules happens to match (a title like "id_rsa rotation") is still committed. Setup refuses ignore rules that hide notebook pages as such, and setup refuses, and sync stops with the same notice, when the owner's attributes and line-ending settings would have Git change a page's line endings on checkout (Git for Windows' `core.autocrlf=true` without `notebook/** -text` or an `eol=lf` attribute). Connecting a separate repository in Settings is refused while this mode is on. Its commits run none of the owner's commit hooks; its push runs the owner's pre-push checks like any other push and carries the owner's unpushed commits with it.
- It does nothing while the repository is in the middle of a merge, rebase, cherry-pick, revert or bisect, while another Git command holds the index, or when the folder is not on its branch. A lock that a killed Git left behind is cleared as above.
- It never rebases. When only the other side moved, the folder fast-forwards to it. When both moved, the merge is built in an index of its own without touching the folder, pushed, and only then does the folder fast-forward to it: the owner's branch only ever takes commits the other side has, so a refused or failed push leaves no merge of the notebook's there for a `git pull --rebase` to replay, and the push carries exactly the commit checked under the lock. Offline nothing is committed; the edits wait as files. Git refuses a fast-forward that would overwrite a file the owner is still editing or an untracked file, so nothing unsaved is lost; the reconciler reports that it is waiting and tries again.
- Before the folder takes the other side's commit or a merge, the notebook it would then read is checked as a full read checks it. A reference to a removed record, a file that does not read, or two records with one identity that the change would bring is not taken: nothing moves, nothing is pushed, what to look at (the removed record, as this machine has it) is saved in `conflicts/`, and the sync reports a conflict. Keeping that record brings it back on the other machines.
- Records renamed or moved on either side are merged by record first (above), in the same index. A path both sides changed is merged line by line when that merges cleanly (a record must still decode; a page that is not a record merges like any file). Otherwise, inside the reconciler's own paths, this machine's version stays (or the surviving one, when the other side deleted it), base, local and remote are saved in `conflicts/` with `kept`, and the merge completes, so the shared branch is never left diverged and a plain `git pull --rebase` elsewhere never meets the conflict. Outside its paths it does not settle anything: the merge is abandoned, nothing is pushed, and the owner's Git settles it. In this mode a saved conflict does not hold back later synchronization; choosing a version is an ordinary edit that syncs like any other.
- A merge that would remove more than 25 records of one type that are also more than a fifth of that type's live pages is not applied, and the same removal made here does not leave. A record that moved is not removed: what counts is the UUIDs gone from every path.

The pre-push checks of the owner's repository treat a push that carries only `notebook/` (or the prompt archive) as having nothing to check.

Exactly one declared owner executes schedules. Pairing transfers jobs to VPS ownership; a network outage never transfers them back. Local-only use retains a declared local owner while the service runs. Explicit owner transfer is required to resume local background jobs. Attempted receipts precede execution. An interrupted or uncertain action pauses for review instead of replaying an unverified side effect.

Prepared multi-file journals contain before/after bytes and a fsynced manifest. Startup rolls a prepared operation forward. A dead process lock can be recovered; a live writer cannot be stolen. Malformed direct edits preserve the original file and surface a validation problem. Search corruption preserves the damaged index separately and reconstructs from files.
