# File sync contract, format 1

The authoritative meeting point is an owner-selected private GitHub repository. Before enabling uploads, unauthenticated GitHub lookup must return 404 and authenticated Git transport must successfully read it. Public repositories and URLs containing credentials are refused. Git credentials remain with the device credential manager. A new empty remote is supported; a GitHub account or repository is never created by setup.

Records use stable UUIDs plus readable IDs with UUID suffixes. Imported IDs and slugs remain unchanged. A record's identity is the `id` and `uid` in its file, never the file's name: a page a person reads is named after its title and sits in its folder (`file-format.md`), so a title, name or folder edit renames or moves the file, and every reference, which is by UUID, stays valid. Explicit id renames retain the previous ID as an alias and atomically rewrite typed references, and keep the file. Removals are tombstones, which leave the readable folders for the system folder. Event edits are appended corrections; prior events remain unchanged. Histories preserve source UUID and exact earlier snapshots.

The reconciler takes the same exclusive workspace lock as record edits, validates, commits only permitted durable text, fetches, merges in a separate disposable worktree, validates the complete result and publishes through the transaction journal, putting every record at the file the merge gave it so that every machine names it the same. It never force-pushes, rebases user work or puts Git conflict markers in notes. A network failure leaves the local files available and records pending status. Existing externally staged files outside permitted state stop uploads. File names are read from Git exactly (null-separated), since a title with an umlaut or an emoji is a file name.

Concurrent same-file edits save base, local, remote and remote commit in conflicts/. Both versions remain readable until the owner chooses one or supplies merged text. An explicit resolution is reused only against that recorded remote commit. A saved conflict about a record follows the record by its UUID, so it can still be resolved after the record's file was renamed. Broken references, invalid files and unproven remote deletion stop publication. Independent offline edits retain distinct identities and converge. Immutable history records have deterministic IDs to avoid false cross-device conflicts.

## Renames and moves

Git is never allowed to infer a rename from content: its merges here use strategies that detect none and its diffs run with `--no-renames`, so it sees a renamed page as one file deleted and another added. Before any file of a merge is called a conflict, the reconciler reads the records the two sides touched on the merge base and on both sides and merges by record, by the UUID in the frontmatter (`notebook/core/sync/identity.mjs`), in both modes below:

- A record changed on one side only arrives as that side has it, where that side put it: a rename syncs as a rename, and the old file goes on every machine.
- A record moved on either side (renamed, moved to another folder, trashed, removed) and changed on both is merged field by field, a text field line by line. A rename on one machine and an edit on another end as one record with both changes, in the renamed file. When both changed the same field differently (two different titles), this machine's version stays, once, and base, local and remote are saved in `conflicts/` as one review item; the other version never lands as a second file.
- Two records that want one file name (the same title created on two machines offline, or a rename into a name the other side used) both stay: the one this machine already had there keeps the name and the other gets ` 2`, ` 3`. Names are compared as a file system that ignores case does. A page that is not a record keeps its name over a record.
- A record moved without being changed (an item whose collection was renamed) stays where the moving side put it.
- A record changed on both sides at the same file is merged line by line as below; a record must still read as one afterwards.
- A page in the notebook folder that is not a record syncs like any other document, never as a record.

A change that moves many records at once (renaming a folder, converting a workspace) is not a mass removal: the removal guards count only records whose UUID is gone from every path.

Records and readable workspace documents sync as files. SQLite, device configuration, credentials, media binaries, node_modules and secrets never enter the knowledge repository. Media uses authenticated HTTP, one-time pairing and persistent device keys. SHA-256 checks every transferred binary. A content-addressed byte file and mapping preserve the storage path. Same-path different bytes create a review item with both versions; keep-both gives the local version a unique retained path. Tombstones propagate only against the same content hash. Bytes are retained for recovery. Offline choice is all media or selected already downloaded paths; selected mode does not evict existing bytes automatically.

## Through the mission control's own repository

A mission control that is already its own private repository, cloned to its owner's machines, can carry the notebook in that same repository instead of a second one (`godspeed sync folder`, which writes `{"repository":"folder","paths":[...]}` to `.godspeed/sync-config.json`). Two carriers delivered every file twice: a file committed on one machine reached the next as an untracked copy through the notebook first, and that machine's own `git pull` then refused to overwrite it. Setup refuses unless the repository is private, on its branch, and already ignores `.godspeed/`, `conflicts/`, `FULL-ALPHA.md` and, unless it is carried, `assistant-state/`. It never edits the owner's ignore file, config or hooks, and sets an older `.godspeed/sync.git` aside without deleting it.

In this mode the reconciler shares the repository with its owner's sessions and scheduled pulls, so it follows their rules rather than its own:

- It commits only its own paths: `notebook/` by default, or every shared path (`"*"`) on a machine where nothing else commits, such as a server. It commits them as a partial commit of exactly those files, so whatever the owner has staged stays staged and out of it. Its commits run none of the owner's commit hooks; its push runs the owner's pre-push checks like any other push and carries the owner's unpushed commits with it.
- It does nothing while the repository is in the middle of a merge, rebase, cherry-pick, revert or bisect, while another Git command holds the index, or when the folder is not on its branch.
- It never rebases. When only the other side moved, the folder fast-forwards to it. When both moved, the merge is built in an index of its own without touching the folder, and the folder then fast-forwards to that merge. Git refuses a fast-forward that would overwrite a file the owner is still editing or an untracked file, so nothing unsaved is lost; the reconciler reports that it is waiting and tries again.
- Records renamed or moved on either side are merged by record first (above), in the same index. A path both sides changed is merged line by line when that merges cleanly (a record must still decode; a page that is not a record merges like any file). Otherwise, inside the reconciler's own paths, this machine's version stays (or the surviving one, when the other side deleted it), base, local and remote are saved in `conflicts/` with `kept`, and the merge completes, so the shared branch is never left diverged and a plain `git pull --rebase` elsewhere never meets the conflict. Outside its paths it does not settle anything: the merge is abandoned, nothing is pushed, and the owner's Git settles it. In this mode a saved conflict does not hold back later synchronization; choosing a version is an ordinary edit that syncs like any other.
- A merge that would remove more than 25 records and more than a fifth of them is not applied. A record that moved is not removed: what counts is the UUIDs gone from every path.

The pre-push checks of the owner's repository treat a push that carries only `notebook/` (or the prompt archive) as having nothing to check.

Exactly one declared owner executes schedules. Pairing transfers jobs to VPS ownership; a network outage never transfers them back. Local-only use retains a declared local owner while the service runs. Explicit owner transfer is required to resume local background jobs. Attempted receipts precede execution. An interrupted or uncertain action pauses for review instead of replaying an unverified side effect.

Prepared multi-file journals contain before/after bytes and a fsynced manifest. Startup rolls a prepared operation forward. A dead process lock can be recovered; a live writer cannot be stolen. Malformed direct edits preserve the original file and surface a validation problem. Search corruption preserves the damaged index separately and reconstructs from files.
