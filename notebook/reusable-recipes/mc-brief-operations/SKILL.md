# Briefing operations

This method governs the daily brief and any later explanation or action based on it. It shares the user's workspace authorization and voice rules. It grants no publishing, sending or spending rights.

## Verify the artifact first

Before asking for a decision, locate the actual artifact through the visible notebook, its location/reference registry or the exact selected repository. Open/read it and check its current version. Only then write the item with its source, relevant exact quote and usable link.

A pointer register is not the artifact. When it cannot be found, remove the decision gate and retain a repair finding stating what was searched and the next authorized attempt. Never ask the user to approve something the assistant has not read, or ask where their artifact lives before searching available knowledge.

## One decision, one link

The link must open the thing being decided in the user's actual context. Use an authenticated notebook link for private knowledge, a verified public source URL for public material, or an existing authorized approval page. A server filesystem path is not a usable phone link. Check access and the destination before describing it as reachable.

Private repository links may require an account and can fail on a phone. Do not silently publish private content to make a link work. Prepare an authorized private notebook artifact or ask only for a genuinely necessary publication approval after the artifact is concrete. Every decision presented to the user carries exactly one link to its subject.

## Experiment gates

Read the actual current experiment/forecast records and their source artifacts. Report open experiments from observed findings with dates. When a trial ends or a gate date arrives, explain what was being tried, what the date means, the latest actual outcome and the next necessary step.

A hands-off experiment reports observable artifacts, not guessed inner state or successful work inferred from a draft. If another session needs a finishing prompt, prepare and read that prompt, then provide its authorized accessible artifact. A registered gate without its supporting result remains unverified.

## Plain choices

Write as though the user saw none of the work. Explain unfamiliar system names in the same sentence or omit them. Do not put internal experiment codes, decision IDs, file paths or tool names in the explanation.

A necessary action has what it is, what happens if ignored, the exact next step and one link. A choice has numbered options with one plain sentence explaining what each answer causes. Preserve a supplied list's exact numbered lines when the user must reply by number. Never summarize away the numbers and still ask for them.

Target dates are desired dates; deadlines carry a consequence. Do not call a missed target costly or overdue. Do not ask the user to judge the assistant's own routine when an authorized repair can be completed independently.

## Follow-up questions and corrections

First find the saved evidence for the exact note/version the user saw. Read its facts, source records and checks, then answer directly in first person. If a claim cannot be reconstructed, say that plainly and verify it again; do not guess or disown the earlier note.

When a claim was wrong, preserve the original delivery and save a dated correction with the evidence and actual repair. A later preview never replaces the received version. Confirm a completed action only after reading back its actual saved result or acknowledgement.
